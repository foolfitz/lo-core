1. High: `XSplitterWindow::setRange()` is implemented as a one-shot snapshot, not persistent state. [`toolkit/source/awt/vclxsplitter.cxx:106`](/home/jiajun/LibreOffice/LO-core/toolkit/source/awt/vclxsplitter.cxx#L106) computes the drag rect from the current parent size and current orientation, but the stored range fields are never reused after assignment in [`toolkit/inc/awt/vclxsplitter.hxx:32`](/home/jiajun/LibreOffice/LO-core/toolkit/inc/awt/vclxsplitter.hxx#L32). After [`toolkit/source/awt/vclxsplitter.cxx:89`](/home/jiajun/LibreOffice/LO-core/toolkit/source/awt/vclxsplitter.cxx#L89) or any parent resize, the splitter keeps the stale drag rect, unlike VCL’s own paned widgets which reapply `SetDragRectPixel` on allocation changes at [`vcl/source/window/layout.cxx:2777`](/home/jiajun/LibreOffice/LO-core/vcl/source/window/layout.cxx#L2777) and [`vcl/source/window/layout.cxx:2896`](/home/jiajun/LibreOffice/LO-core/vcl/source/window/layout.cxx#L2896). This will make the advertised range silently stop matching actual drag behavior; the fix is to factor out `applyRange()` and call it from `setRange`, `setHorizontal`, `SetWindow`, and resize handling.

Since this peer still exposes `XWindow`, callers can reasonably attach `XPaintListener` and expect normal toolkit behavior, but they will never receive events.
